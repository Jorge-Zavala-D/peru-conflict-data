The admitted destinations hold detailed immutable evidence, not command stdout.

`capture` is bounded to one schedule action, not necessarily one HTTP request:
account/prerequisite observations and bounded pagination belong to that action.
An acknowledged asynchronous job permits the existing bounded status action, not
another sharing mutation. There is no loop-to-completion command. A completed

separate `capture` process works only because `next` is a nonexecuting preview.
No executable release is serialized to a caller-controlled file.

Exit 0 means inspection/initialization or the bounded action returned normally;
it does not mean setup is complete or approved. Exit 2 means rejected arguments,
startup/admission or unreadable/inconsistent history. Exit 3 means the requested
action is stopped, pending or incomplete. Successful inspection can report
UNKNOWN, INTENT_PENDING, STOPPED or PENDING with exit 0. FAIL and INCONCLUSIVE
remain evidence results; COMPLETED remains a procedure state, never owner approval.
Inspection takes the existing exclusive kernel writer lock, but never rewrites
immutable claims, records or checkpoints. Missing history is not a new run.

Transferred originals are retained only under the independently admitted witness

sources do not become evidence. A copied capture and its own uploaded digest
